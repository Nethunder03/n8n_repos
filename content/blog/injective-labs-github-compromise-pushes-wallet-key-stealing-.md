# Attaque Supply Chain sur Injective Labs : Des paquets npm malveillants dérobent les clés de portefeuilles crypto ![Compromission du GitHub d'Injective Labs : Des paquets npm malveillants dérobent les clés privées de portefeuilles crypto](https: Une cyberattaque sophistiquée de type *Supply Chain Attack* (attaque de la chaîne d'approvisionnement) a récemment frappé l'écosystème de développement d'**Injective Labs**. Des attaquants ont réussi à compromettre le dépôt GitHub officiel du projet pour y introduire du code malveillant, entraînant la publication d'une version compromise de leur SDK sur le registre public npm. Le but de cette campagne ? Voler les clés privées et les phrases de récupération (seed phrases mnémoniques) des portefeuilles de crypto-monnaies des utilisateurs. --- ## Les détails techniques de la compromission L'attaque a ciblé le paquet npm officiel de l'entreprise : . Le 8 juillet 2026, la version **1.20.21** a été publiée avec un composant malveillant intégré. Selon les rapports d'analyse de Socket et d'OX Security, la compromission n'a pas été réalisée via le vol d'un token d'accès direct au registre, mais à la source même, sur GitHub. L'attaquant a pu pousser des modifications de code directement sur le dépôt officiel en usurpant ou en compromettant le compte d'un contributeur établi et de confiance, connu sous le pseudonyme de . Les commits malveillants ont ensuite été validés et publiés via le pipeline CI/CD automatisé du projet, qui utilise la technologie de fédération d'identité **OIDC (OpenID Connect)** en tant que *trusted publisher*. ## Une furtivité remarquable Pour éviter les alertes des scanners de sécurité automatiques qui analysent les paquets npm à la recherche de comportements suspects, les attaquants ont fait preuve de discrétion : - **Pas de scripts d'installation :** Le malware n'utilise aucun script de cycle de vie (, ). Il reste totalement inactif lors de la phase d'installation du paquet. - **Exécution conditionnelle :** Le code malveillant se déclenche uniquement lorsque les fonctions du SDK sont appelées par l'application pour générer des clés privées. - **Fausse télémétrie :** L'injection se dissimule derrière une fonction appelée . Les commentaires du code affirmaient mensongèrement que cette fonction servait à collecter des métriques anonymes de performance pour optimiser le SDK. Une fois activé, le logiciel espion intercepte les paramètres de dérivation de clés, y compris les phrases mnémoniques (qui agissent comme la clé maîtresse de n'importe quel portefeuille crypto). Afin de réduire le bruit réseau et d'éviter d'éveiller les soupçons avec de multiples requêtes, le malware stocke les informations volées dans une file d'attente locale pendant une fenêtre temporelle de deux secondes avant de les envoyer d'un seul bloc (HTTPS POST) vers le domaine externe : . --- ## Quel est l'impact pour les utilisateurs ? L'impact de cette attaque est particulièrement lourd et s'étend bien au-delà de la seule bibliothèque principale. L'attaquant a également republié la version compromise 1.20.21 sur **17 autres paquets** du scope qui dépendaient directement de cette version spécifique du SDK. Cela signifie que même si un développeur n'a pas installé directement la bibliothèque compromise, il a pu l'importer de manière indirecte (dépendance transitive) via d'autres outils officiels d'Injective Labs. Toutes les applications web, scripts ou services backend ayant utilisé cette version spécifique du SDK entre le 8 juillet et sa dépréciation officielle ont potentiellement exposé les secrets cryptographiques de leurs utilisateurs à des tiers non autorisés. Grâce à ces données, les attaquants sont en mesure de régénérer intégralement les portefeuilles cibles à distance et de vider les fonds associés. --- ## Recommandations et mesures de remédiation Si vous êtes développeur ou utilisateur d'outils intégrant les packages d'Injective Labs, il est impératif d'appliquer immédiatement les mesures suivantes : 1. **Mise à jour d'urgence :** Mettez à jour le package et toutes ses dépendances vers la version propre **1.20.23** (ou supérieure), publiée par l'équipe officielle. 2. **Rotation et migration des actifs :** Considérez toute clé privée ou phrase mnémonique générée, importée ou lue via la version compromise 1.20.21 comme définitivement corrompue. Créez de nouveaux portefeuilles sécurisés à partir d'une installation propre et transférez-y immédiatement l'intégralité de vos fonds. 3. **Audit des dépendances transitives :** Utilisez des commandes telles que ou pour identifier si une version compromise est toujours présente dans vos environnements de production ou de développement. 4. **Sécurisation des pipelines de publication :** Pour les équipes de développement, revoyez l'accès de vos pipelines de déploiement basés sur OIDC, limitez les privilèges de publication automatique et imposez une authentification multifacteur (MFA) stricte pour chaque développeur ayant des droits d'écriture sur les dépôts de code source. --- ## Sources Source: The Hacker News - https:
