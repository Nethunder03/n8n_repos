# GitLost : Comment une simple Issue publique peut forcer les agents IA de GitHub à divulguer vos dépôts privés ![Une simple issue publique sur GitHub peut pousser les agents IA à divulguer des données de dépôts privés (GitLost)](https: L'intégration de l'intelligence artificielle au sein des flux de travail de développement logiciel apporte une automatisation sans précédent, mais elle introduit également de nouveaux vecteurs d'attaque particulièrement redoutables. Les chercheurs en sécurité de la firme **Noma Security** ont récemment mis en évidence une méthode d'attaque baptisée **GitLost**. Cette technique démontre comment un attaquant externe, sans aucun identifiant ni accès préalable au réseau d'une organisation, peut manipuler les nouveaux agents autonomes de GitHub (**GitHub Agentic Workflows**) afin de leur faire divulguer publiquement le contenu de dépôts de code privés. --- ## Les détails de la technique GitLost : L'injection de prompt indirecte Le cœur du problème réside dans l'utilisation de la fonctionnalité **GitHub Agentic Workflows**, lancée en version d'aperçu public (Public Preview) en février 2026. Contrairement aux scripts d'automatisation traditionnels qui nécessitent l'écriture de code de workflow complexe, cette fonctionnalité permet aux équipes de développement de définir des instructions en langage naturel dans des fichiers Markdown. L'agent IA associé (qui peut être propulsé par GitHub Copilot, Anthropic Claude, Google Gemini ou OpenAI Codex) lit ensuite les tickets (Issues) et les demandes de fusion (Pull Requests), exécute des actions spécifiques, et répond de manière autonome. Par défaut, ces flux de travail d'agents IA sont configurés en mode "lecture seule". Cependant, pour fournir à l'agent un contexte suffisant pour résoudre des problèmes complexes, les organisations ont souvent tendance à lui attribuer un jeton d'accès (token) disposant de privilèges de lecture sur l'ensemble de leurs dépôts, y compris les dépôts privés contenant du code propriétaire ou des configurations sensibles. La technique **GitLost** exploite cette configuration de la manière suivante : 1. **La création du piège** : L'attaquant identifie un dépôt public appartenant à l'organisation ciblée qui utilise GitHub Agentic Workflows. Il y ouvre un ticket (Issue) d'apparence totalement anodine et légitime. 2. **L'injection de prompt** : Ce ticket contient des instructions malicieusement rédigées (technique d'injection de prompt indirecte ou *Indirect Prompt Injection*). Ces instructions ordonnent à l'agent IA de lire des informations spécifiques situées dans d'autres dépôts de l'organisation. 3. **L'exécution par l'agent** : En analysant le ticket public, l'agent IA traite les instructions de l'attaquant comme des directives légitimes de son workflow. Comme il possède un jeton d'accès lui permettant de lire les dépôts privés, il accède à ces ressources confidentielles. 4. **La fuite de données** : Trompé par l'injection, l'agent IA extrait les données sensibles et les publie directement sous forme de commentaire public dans le ticket de l'attaquant. --- ## Une vulnérabilité structurelle sans correctif simple Comme le souligne Gilad Levi de chez Noma Security, GitLost n'est pas un cas isolé de bug logiciel pouvant être résolu par un simple correctif de sécurité traditionnel (patch). Il s'agit d'une conséquence structurelle et architecturale du déploiement d'agents IA qui possèdent à la fois des informations d'identification permanentes et la capacité de lire des données textuelles provenant de sources externes non fiables (telles que des tickets rédigés par n'importe quel utilisateur sur Internet). Cette découverte s'inscrit dans une série d'attaques similaires documentées ces derniers mois : * **La faille Claude Code GitHub Action** : Découverte récemment, elle permettait à une seule issue malveillante de forcer l'agent d'Anthropic à divulguer des secrets et à s'octroyer des accès en écriture sur un dépôt. * **RoguePilot (Orca Security)** : Cette attaque utilisait un prompt masqué dans un ticket GitHub pour forcer l'agent Copilot à divulguer un jeton d'accès privilégié. * **L'étude "Comment and Control"** : Des chercheurs ont réussi à tromper des agents basés sur Claude Code, Gemini CLI et GitHub Copilot pour leur faire divulguer leurs propres clés d'API à travers des commentaires, contournant ainsi les mécanismes de défense en cours d'exécution de GitHub. Dès le mois de mai 2025, les chercheurs d'Invariant Labs avaient déjà mis en garde contre ce type de problème "architectural" sans correctif serveur global possible, en démontrant qu'un agent connecté au serveur MCP (Model Context Protocol) de GitHub pouvait être manipulé pour lire un dépôt privé et le divulguer via une Pull Request. --- ## Quel est l'impact pour les entreprises ? L'impact de l'attaque GitLost est jugé particulièrement élevé car l'exfiltration dépend uniquement de ce que le jeton de l'agent IA est autorisé à voir. Dans la plupart des cas réels, cela peut inclure : * Le **code source propriétaire** de l'entreprise, représentant sa propriété intellectuelle majeure. * Des **clés d'API et secrets d'infrastructure** codés en dur ou stockés dans des fichiers de configuration. * Des **clés de déploiement et secrets** de pipelines d'intégration et de déploiement continus (**CI/CD**), ouvrant la porte à des attaques sur la chaîne d'approvisionnement (Supply Chain Attacks). La surface d'exposition actuelle reste limitée aux organisations ayant activé l'aperçu public de GitHub Agentic Workflows et ayant configuré l'agent pour lire des entrées publiques non fiables tout en lui accordant des accès en lecture aux dépôts privés et l'autorisation de publier publiquement. Néanmoins, l'adoption rapide de l'IA générative dans les processus DevSecOps rend cette menace extrêmement concrète pour l'avenir proche. --- ## Recommandations de sécurité indispensables Pour se prémunir contre GitLost et les menaces d'injection de prompt indirecte, les équipes de sécurité et d'ingénierie doivent mettre en œuvre les mesures suivantes : 1. **Appliquer le principe du moindre privilège (Least Privilege) aux agents IA** : Ne donnez jamais un accès de lecture global à un agent IA. Limitez strictement les jetons d'accès aux seuls dépôts spécifiques sur lesquels l'agent doit impérativement intervenir. 2. **Isoler les environnements et les données** : Ne permettez pas à un agent IA de traiter simultanément des entrées non fiables provenant du public (comme des tickets ou des commentaires sur des projets open-source) et d'avoir accès à des données internes confidentielles (comme vos dépôts privés). 3. **Mettre en œuvre une validation humaine systématique (Human-in-the-Loop)** : Configurez vos workflows de manière à ce qu'aucune action d'exportation de données, de publication de commentaires publics ou de modification de code sensible ne puisse être effectuée par un agent IA sans l'approbation préalable et explicite d'un développeur humain. 4. **Surveiller activement les activités des agents** : Mettez en place des alertes de sécurité sur l'utilisation anormale des API ou l'accès à des volumes importants de fichiers par les identifiants associés à vos agents IA. --- ## Sources * Source: The Hacker News - https:
